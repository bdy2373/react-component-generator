# Commit

## 1. 변경사항 분석

- `git rev-parse --show-toplevel`로 저장소를 확인하고 적용되는 `AGENTS.md` 지침을 읽는다. 저장소가 아니면 커밋할 수 없음을 알리고 중단한다. 임의로 `git init`하지 않는다.
- `git status --short`, `git diff --stat`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 분석한다.
- 추적되지 않은 파일은 diff에 나오지 않으므로 상태 목록에서 확인하고, 커밋 후보 파일의 내용을 별도로 읽는다. 비밀 키나 `.env`의 실제 값은 출력하거나 커밋하지 않는다.
- 변경사항이 없으면 이를 알리고 종료한다.

## 2. 논리적 단위 분류

- 파일 확장자나 폴더가 아니라 변경 목적을 기준으로 묶는다. 하나의 기능에 필요한 코드·스타일·테스트는 같은 단위로 다룬다.
- 독립적인 변경은 별도 커밋으로 나눈다. 같은 파일에 서로 다른 목적의 변경이 있으면 필요한 부분만 선택적으로 스테이징한다.
- 기존 스테이징 상태와 사용자 변경을 존중한다. 내용을 되돌리거나 덮어쓰지 않고, 무관한 변경을 끼워 넣지 않는다.

## 3. 한국어 커밋 메시지 작성

형식은 `<type>: <한국어 요약>`으로 한다. 요약은 변경된 동작이나 목적을 구체적이고 간결하게 쓴다.

| 타입 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 | `feat: 생성 결과 다운로드 기능 추가` |
| `fix` | 오류 수정 | `fix: 빈 프롬프트의 생성 요청 차단` |
| `refactor` | 동작을 유지하는 구조 개선 | `refactor: 컴포넌트 생성 API 호출 분리` |
| `chore` | 설정·문서·도구·유지보수 | `chore: 커밋 작업 스킬 추가` |

## 4. 별도 승인 없이 커밋

- 사용자의 커밋 요청을 실행 권한으로 간주한다. 커밋별 대상과 메시지를 준비한 뒤 추가 승인 질문이나 대기 없이 커밋한다. 사용자가 이번 작업에 별도 확인을 명시한 경우에는 그 지시를 따른다.
- 실행 전에 커밋 범위와 메시지를 간단히 알린다. 검증 결과는 완료 보고에 포함하고, 검증하지 않았다면 그렇게 명시한다.
- 스테이징 직전에 변경 상태를 다시 확인하고 요청 범위에 맞춰 커밋 대상을 확정한다. 범위가 명확하면 파일 분류와 메시지는 스스로 결정한다.
- 요청한 파일 또는 부분만 명시적으로 스테이징한다. `git add .`나 `git add -A`로 모든 변경을 일괄 포함하지 않는다. `git diff --cached`로 실제 커밋 대상이 요청 범위와 일치하는지 확인한다. 기존에 스테이징된 무관한 변경이 있으면 그대로 포함하지 말고 요청 범위만 커밋할 방법을 선택한다.
- 작성한 메시지로 `git commit`을 실행한다. 여러 커밋은 논리적인 순서대로 진행하며, 실패하면 후속 커밋을 멈추고 원인을 알린다. 훅이나 검증을 임의로 우회하지 않는다.
- 완료 후 `git log`와 `git status --short` 등을 확인해 생성된 커밋 해시·메시지와 남은 변경사항을 보고한다.
- 별도 요청 없이 push, amend, reset, 이력 재작성은 수행하지 않는다.
